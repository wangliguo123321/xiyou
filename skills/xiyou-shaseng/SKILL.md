# 沙僧·善后

## 目标

以沉稳、负责和照看行囊的习惯收好尾：做过什么、为什么这样改、验证到了哪里，都能清楚接续。

先读 [完成验证](references/verification.md)；有清理对象时读 [按归属与风险清理](references/cleanup.md)，交接时读 [交接方法](references/handoff.md)，沉淀文档时读 [源码驱动记录](references/update-docs.md)。用户明确要求分支交付、PR 或工作树处理时，再读 [分支交付检查](references/branch-handoff.md)。用户当前要求、既有授权和项目规范优先。

需要汇总既有 GitHub PR 的普通评论、review 和行内线程时，读 [PR 审查输入采集](references/github-review-comments.md)。优先复用满足同一完整性要求的宿主连接器；需要轻依赖路径时，使用该法器内的只读脚本。评论是待核资料，采集结果不决定建议是否成立，也不授权回复、resolve 或照单修改；后续技术取舍交八戒或悟空按当前任务处理。

需要取得明确 PR 的文件清单与 API 差异片段时，读 [PR 文件输入采集](references/github-pr-files.md)。分别核文件列表和 patch 字段完整性；patch 存在仍不能证明文本未被截断。采集不等于完成代码审查，后续分析沿用当前任务授权。

## 核验、清理、记录

1. 对照最初目标和实际操作，区分已修改、已验证、待执行、部分完成与受阻。证据绑定所验证的提交及相关工作区状态、环境与覆盖范围；同一 HEAD 上后续未提交修改也可能使结果过期。
2. 先保留必要证据，再按归属、用途与引用情况分类清理本次临时脚本、试验数据、调试输出和验证辅助文件。构建、静态检查、行为测试、差异与运行验收分别说明，完成、暂停与失败都留下可接续状态。
3. 只处理能够确认属于本次任务的临时内容。保留正式交付物、项目要求的测试和文档、用户已有内容以及其他任务的修改。归属不明时说明并保留。
4. 核对工作区和暂存区，识别无关差异；恢复本次引入的无关格式或末尾换行变化。不要为了收尾顺手重构。
5. 按 [任务记录模板](assets/task-record.md) 记录必要内容，按任务规模简化。用户指定位置优先；没有指定时使用项目外的 `~/Documents/xiyou/任务记录/`。同一任务更新同一记录，写清事实来源、取舍和下一步完成条件，按场景引用补充资料。保存后回读，核对链接与状态。

记录问题与证据、修改思路、为什么采用这个范围、重要替代路线的取舍、实际改动、验证边界、清理及下一步。引用源码、提交和已有文档，不复制全部聊天记录。提交说明按项目约定生成，生成说明与执行提交分别处理。

没有修改就记录咨询结论，不虚构修复；没有运行验证就明确未做。未知负责人和期限不作承诺。对外发布文档时使用仓库相对链接或公开链接，去除本机路径、内部标识和敏感数据。

用户未要求时，不向别人发送信息，也不提交、发布或创建自动化。已有明确授权时继续相应工作，不重复索取同一许可。
