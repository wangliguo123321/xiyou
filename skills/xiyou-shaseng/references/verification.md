# 结论与证据对应

> 证据先于结论继承自 Superpowers；分层报告借鉴 ECC `verification-loop`。来源、固定版本和许可证见 [上游致谢](lineage.md)。

## 确定主张 → 获取证据 → 读取结果 → 限定结论

每个完成主张需要对应的可观察结果。先确定什么能证明它，执行适当验证或复用仍对应当前代码状态的结果，检查完整输出、退出状态及覆盖范围，再下结论。

| 主张 | 所需证据 |
|---|---|
| 文件修改完成 | 实际文件与差异 |
| 编译成功 | 对应代码版本的构建结果 |
| 原问题解决 | 原场景或有代表性的行为验证 |
| 需求满足 | 对照要求及相关验证 |
| 构建包可交付 | 实际构建、包标识、有效链接与来源 |
| 设备验收 | 对应设备、环境、版本及反馈 |

子代理报告也需要结合产物与证据核对。部分检查证明的范围如实保留，不能向未覆盖部分推广。验证失败就记录失败，不能使用模糊措辞暗示已经成功。

## 证据对应哪个状态

对必要检查保留命令或操作、结果与退出状态、时间、环境，以及实际验证的代码状态。提交号之外，还要辨别相关未提交修改；可引用差异快照或产物标识，不要求每项都新增校验脚本。测试后代码又改了、配置或运行条件变了，就核对影响，补做受影响检查。仅 HEAD 没变不能证明证据仍有效。

## 按层报告，不用一个“通过”覆盖全部

| 层次 | 说明什么 |
|---|---|
| 构建 | 此代码状态在指定目标与配置下能否编译或打包 |
| 静态检查 | 类型、规则等工具实际覆盖范围及结果 |
| 行为测试 | 哪些场景、回归或边界得到了验证 |
| 差异检查 | 需求对应关系、工作区与暂存区范围、临时产物清理 |
| 包、发布或设备 | 实际产物、目标环境和运行反馈，按任务需要提供 |

每项标明通过、失败、未运行、过期、受阻或不适用；不适用要有理由。完成已做的检查不等于任务已完成，也不等于代码已提交或发布。失败、暂停时继续保存证据和交接，保留尚未达到的完成条件。

## 西游适配

继承证据先于主张与分层报告，不照搬“每次说话必须重新运行所有检查”。源码与条件未变化可复用有效证据；材料过期或目标变化时补验。使用当前项目实际命令、需求与质量门禁，不套固定语言、覆盖率阈值、时间间隔或 `HEAD~1` 基线。临时验证资源及时清理。缺少设备时报告编译通过、设备待验，而非假装全过或抹去已经完成的工作。
