# 核验评审建议

> 基于 Superpowers `receiving-code-review` 适配；固定来源与许可见 [上游致谢](lineage.md)。

## 理解建议，再决定改动

1. 把建议还原成要解决的问题、成立条件和预期行为。评审者的职位、措辞或“最佳实践”标签不能代替技术依据。
2. 核对当前调用者、已有能力、兼容条件和采用现有实现的原因。涉及通用化时，查真实复用需求及维护成本；静态未找到调用只能说明当前搜索结果，还要按需要检查动态或外部调用。
3. 分别判断：有依据且在范围内就采纳；方向合理但过重就提供更小的实现；与事实或既有决定冲突就说明理由；关键证据缺失则写出最小核验动作。
4. 有疑问时只暂停依赖该疑问的部分。能由代码或已有资料核实的先查；需要用户决定的明确提问，其他已授权且独立的工作继续。
5. 已授权修改时落实必要调整，验证被影响行为；只要求审查时交付判断。新证据推翻先前意见时修正结论。

## 常见意见怎样处理

| 意见 | 核验重点 |
|---|---|
| “再通用一点、加个管理器” | 哪些已确认调用场景需要它；现有路径或局部函数能否满足 |
| “把这个兼容分支删了” | 支持版本、真实调用与失败行为是否允许删除 |
| “已有工具能做这件事” | 实际接口、边界语义和项目依赖是否匹配 |
| “以后可能需要” | 是已确认需求还是设想；设想单列，不直接增加实现 |

回复包含处理决定、证据和下一步，避免先承诺照办再找理由。若用户已批准该改动，不因评审流程再次索要同一授权。

## 西游适配

保留理解、核验、取舍和验证；不继承一条不明意见阻塞全部工作的规则、固定话术禁令或自动回复外部评审线程。评审记录与向他人发送消息分别处理。
