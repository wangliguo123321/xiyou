# 先找已有能力

> 基于公开上游的中文适配；来源、固定版本和许可证见 [上游致谢](lineage.md)。

## 需求 → 搜索 → 评估 → 选择 → 最小适配

新增工具、公共方法、依赖或抽象前，确定需要的功能和语言/平台约束。先查当前仓库，再按需要查已有工具、已安装技能、维护中的库与公开实现。

使用前核对搜索渠道可用性。缺少渠道要说明未覆盖，不把没搜到和渠道不可用混为一谈。候选评价功能匹配、维护、社区、文档、许可证与依赖负担。

| 情况 | 选择 |
|---|---|
| 现有能力完整匹配 | 直接采用 |
| 基础合适但有明确缺口 | 小幅扩展或薄封装 |
| 几个小能力能完成需求 | 按清晰边界组合 |
| 已查证没有合适基础 | 根据证据构建最小实现 |

## 采用前的兼容性核验

对拟采用的能力核对接口、输入输出、错误语义、平台限制与新增依赖，安排能够验证关键需求的最小行为检查。无法执行时标为待验证；安装成功或资料声称支持不能代替集成验证。

比较结果至少说明候选的来源/版本、满足的需求、明确缺口、适配成本、已覆盖的验证与推荐依据。本地已有充分证据时结束搜索，不为了填表继续增加候选。

## 两个上游示例的场景适配

- **HTTP 客户端：** 先核对项目已有客户端能否满足所需超时、重试和错误处理；满足就复用，有明确缺口才作薄适配。具体库的能力按版本验证，不沿用上游示例中的生产可靠性背书或固定评分。
- **配置校验：** 由成熟通用校验能力负责校验机制，项目只维护自己的规则。核对现有校验器后再选依赖，用有效和无效配置检查关键行为，不为一个规则集重写通用校验框架。

## 西游适配

此流程也用于检查 AI 的方案是否重复造轮子。对已经明确的局部缺陷，优先看现有代码，不强制全网研究。外部复用的集成成本也计入判断，不为一项小功能引入巨大依赖。移除固定包名、安装命令和必须启动 researcher 的要求；真正需要外部工具时使用当前授权和可用接口。
